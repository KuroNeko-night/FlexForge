# FlexForge 可行性评审

**版本**：v0.1  
**评审日期**：2026-08-20  
**评审结论**：有条件可行

## 1. 结论摘要

FlexForge 作为毕业设计是可行的，工程上也有清晰的演示价值；但原始设想的范围接近一个长期演进的产品平台。若同时实现完整 ERP、元数据引擎、插件市场、工作流设计器和自主 Agent，项目很容易在集成、测试和安全上失控。

参考 dsh 后，建议将答辩主线收敛为四个可验证能力：

1. 元数据定义实体、字段和视图，并动态生成 CRUD。
2. 运行时插件注册表、版本化激活和生命周期管理。
3. Issue -> AI 结构化需求 -> 插件骨架 -> 人工审核的闭环。
4. 一个最小业务示例（建议“物料/库存”或“销售订单”二选一）。

轻量工作流可以作为加分项，仅实现数据变更触发、条件判断、更新字段和站内通知四种动作。插件市场只做本地/内部上传下载，不做开放生态。

## 2. 可行性评分

| 维度 | 判断 | 说明 |
| --- | --- | --- |
| 技术可行性 | 高 | Vue、Spring Boot、关系型数据库和 LLM API 均有成熟实现路径。 |
| 需求可控性 | 中 | 原始范围过大；按 MVP 裁剪后可控。 |
| 学术/答辩价值 | 高 | 元数据驱动、插件化和 AI 辅助开发具有清晰的设计与实验对象。 |
| 个人工作量 | 中-高 | 需要同时处理前后端、动态渲染、插件生命周期和 AI 集成。 |
| 外部依赖风险 | 中 | LLM API、模型输出质量、部署环境可能影响演示。 |
| 交付风险 | 中 | 采用模块化单体、模板优先和人工审核后，风险可降到可接受水平。 |

## 3. 核心风险判断

### 3.1 最大风险：范围膨胀

“企业级平台”不是单个功能，而是权限、数据、部署、升级、兼容和运营体系的集合。毕业设计应证明关键机制，而不是覆盖所有企业场景。

### 3.2 动态数据库结构的复杂度

完全根据用户输入执行任意 `CREATE TABLE` 和动态 SQL，会引入 SQL 注入、迁移失败、字段变更和回滚问题。MVP 采用受限字段类型白名单、参数化查询和统一动态数据表（或受控表结构）更稳妥。

### 3.3 插件“代码执行”风险

不建议在 MVP 中安装任意后端可执行代码。第一版插件应优先是“声明式插件”：`plugin.json` + 元数据 + 页面/菜单配置 + 迁移脚本，并通过预定义 Service/Extension Registry 接入平台。后端扩展只允许内置编译插件，避免实现沙箱。

### 3.4 AI 输出不稳定

AI 不应直接发布到生产。必须使用 JSON Schema 校验、字段白名单、预览、人工确认、测试环境安装和失败回滚。即使模型不可用，也要支持手工填写结构化需求完成主流程。

## 4. 推荐 MVP 边界

### 必做

- 用户登录和最小 RBAC（管理员、开发者、普通用户）。
- 实体/字段/列表视图元数据配置。
- 动态列表、查询、表单、详情和基础校验。
- 声明式插件的导入、校验、安装、启用、停用和卸载。
- 插件运行时注册表、版本号、激活尝试和失败诊断。
- Issue 状态流转、评论和结构化需求规格。
- AI 需求澄清和插件骨架生成；支持模型失败时的手工兜底。
- 一个完整示例业务模块。
- 审计日志、Docker Compose 一键启动、演示数据和测试报告。

### 可选加分项

- 四节点以内的轻量动作链工作流。
- 本地插件市场列表和版本展示。
- 需求规格到 OpenAPI/前端页面骨架的生成。

### 明确不做

- 完整 ERP 财务、采购、生产、报表体系。
- 通用 BPMN 图形设计器、会签、并行网关和复杂补偿事务。
- 任意第三方可执行代码的在线沙箱。
- 多租户、计费、开放开发者注册和公网插件分发。
- 无人工审核的自动生产发布。
- 任意 Java/JavaScript 插件代码执行和在线沙箱。

## 5. 成功标准

在没有预置业务表的前提下，演示者可以在 10 分钟内完成以下流程：

1. 创建“物料”实体，添加名称、编码、库存数量和状态字段。
2. 保存后立即看到动态生成的列表和编辑表单。
3. 通过 AI 对话或手工规格创建 Issue。
4. 审核 Issue，生成并预览声明式插件。
5. 安装插件，菜单和页面出现；停用后不可访问，卸载后注册信息被清理。
6. 查看关键操作审计日志，并运行自动化测试证明主流程可重复。

## 6. 需要尽早确认的问题

- 最终示例业务选择“库存”还是“销售订单”。建议先选库存，关系更少、演示更直观。
- 是否必须使用某个指定模型或学校内网环境。实现应保留 OpenAI 兼容接口和手工兜底。
- 毕业设计剩余周数、个人投入时间和是否有同学协作。计划书按 16 周编排，可按实际日期压缩。
- 数据库最终选 PostgreSQL 还是 MySQL。建议统一 PostgreSQL，减少动态 JSON 和迁移差异。

> **结论回写（2026-08-20）**：示例业务已选**库存**、数据库已定 **PostgreSQL**（P00 冻结）；答辩目标 **2027 年 5 月中旬**、中期检查 **2027 年 1 月**、每周投入按 20-25 小时编排，倒排表见 `docs/01-project-plan.md` §2.1。模型接口可用性**尚未确认**：开发期按 fixture 优先策略推进，P01 验收时记录最终结论。
