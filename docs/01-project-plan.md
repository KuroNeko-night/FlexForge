# FlexForge 项目计划书

**计划版本**：v0.2  
**适用周期**：2026-08-20 起步至 2027 年 5 月中旬答辩（约 39 周），按每周 20-25 小时投入编排  
**项目形态**：个人毕业设计，模块化单体 Web 系统

详细实施阶段、每阶段验收标准和当前进度锚点见：[详细实施阶段计划](./09-detailed-implementation-plan.md)、[STATUS.md](../STATUS.md)。

## 1. 项目目标

### 1.1 总目标

实现一个可运行、可演示、可测试的模块化数据管理系统，验证元数据驱动、声明式插件和 AI 辅助需求到插件骨架生成的可行性。

### 1.2 可交付成果

- 可启动的前后端应用和 PostgreSQL 数据库。
- 元数据配置与动态 CRUD 页面。
- 声明式插件包示例及生命周期管理。
- Issue 与 AI 结构化需求流程。
- 一个库存或销售订单示例模块。
- 自动化测试、演示脚本、部署说明和毕业论文所需设计材料。

## 3. 工作分解

### 3.1 产品与需求

- 编写用户故事、验收标准和非目标列表。
- 维护需求规格 Schema 和版本变更记录。
- 每个功能建立 Issue，禁止只在聊天记录中留需求。

### 3.2 后端

- 统一错误模型、认证授权、数据库迁移和审计日志。
- 元数据服务：实体、字段、视图、字段校验和数据访问。
- 插件运行时：Service/Extension Registry、激活上下文、disposer 和 stale 请求拒绝。
- Issue/Agent 服务：状态机、任务记录、模型适配和人工确认。

### 3.3 前端

- 登录、工作台、系统管理基础页面。
- 元数据配置页面和动态 CRUD 渲染器。
- 插件管理、Issue、AI 对话和生成预览页面。
- 错误、空状态、加载和权限拒绝状态。

### 3.4 质量与交付

- 单元测试、API 集成测试、端到端冒烟测试。
- 所有阶段遵守 [工程质量与可扩展性治理基线](./10-engineering-governance.md)、[扩展点登记册](./extension-points.md) 与 [回归测试计划](./11-regression-test-plan.md)。
- 演示数据、Docker Compose 和故障排查手册。
- 每个里程碑保留截图、测试结果或录屏作为证据。
- 对插件安装失败、重复注册、依赖缺失和过期激活保留诊断证据。

## 4. 资源与依赖

- JDK 17、Node.js LTS、PostgreSQL 14+、Docker Desktop。
- 一个 OpenAI 兼容的模型接口；模型不可用时使用固定 fixture。
- Git 仓库和 CI（构建、测试、格式检查）。
- 个人每周约 20-25 小时开发时间；若少于此时间，应删除 M7 加分项。

## 5. 验收指标

| 指标 | 目标 |
| --- | --- |
| 核心流程成功率 | 在干净数据库上连续 3 次完成端到端演示 |
| 动态实体创建耗时 | 常规实体保存后 3 秒内可访问 |
| API 性能基线 | 主要 CRUD 接口 P95 < 500 ms（本地演示数据量下） |
| 测试覆盖 | 核心领域服务和状态机有单元测试；主流程有 E2E 冒烟测试 |
| 可部署性 | 按部署文档在新环境启动成功 |
| AI 可靠性 | 无模型时可手工完成；模型输出必须通过 Schema 校验 |

## 6. 风险与应对

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| 范围失控 | 连续两周没有可运行增量 | 冻结新需求，删除可选项 |
| 动态 SQL 缺陷 | 出现注入或迁移不可逆 | 只使用白名单和参数化 API，禁止拼接用户输入 |
| AI 不稳定 | 规格 JSON 频繁无法校验 | 固定 Schema、重试上限、人工编辑和 fixture |
| 插件安装破坏系统 | 安装后无法回滚 | 事务化迁移、版本记录、停用优先于删除 |
| 环境差异 | 本地能跑、演示机不能跑 | Docker 固化版本，每个里程碑在干净环境验证 |
| 时间不足 | 2027-01-15（中期检查）时 P06 未完成，或 2027-03-31 时 P12 未完成 | 删除 P13 与全部可选项；AI 链路收缩为 fixture 单路径；只保留元数据+插件+Issue/AI 主线 |

## 7. 变更控制

新增需求必须说明：价值、影响模块、预计工时、测试方式和对答辩主线的影响。以下任一情况发生时，需求自动降级为候选项：

- 不能复用现有核心模型或扩展点。
- 需要引入新的基础设施或长期维护依赖。
- 会改变已验收的插件格式或规格 Schema。
- 没有明确的演示和测试场景。

## 8. 阶段推进规则

- 阶段编号以 `P00-P14` 为准；旧版 M0-M9 只作为论文时间线的粗粒度映射。
- 每个阶段必须有明确的退出条件和验收证据，未通过时不得进入下一阶段。
- `P13` 是候选阶段，默认不做；仅当 P12 提前于 2027-03 下旬目标完成且无 P0/P1 缺陷时评估启动，任何时候都可以删除，不得影响 `P12` 和 `P14`。
- 当前阶段、下一步、阻塞项和更新时间统一维护在根目录 `STATUS.md`；机器读取使用 `docs/project-status.json`。
