# ADR-0004：系统骨架不含业务，演示示例也必须是可停用插件

**状态**：Accepted
**日期**：2026-08-20
**参考**：[ADR-0002](./0002-runtime-plugin-model.md)

## 背景

毕业设计系统通常会把用于展示的示例业务直接编译进主体代码，导致"演示功能关不掉、删不净"。本项目以"插件可管理"为创新点之一：若连原生自带的演示业务都无法通过插件管理关闭，就说明插件生命周期机制没有真正生效。

ADR-0002 允许 Level 0 内置编译插件承载"复杂服务"，但没有禁止它承载业务能力，存在把库存等业务写进 `flexforge-*` 编译产物从而绕过插件管理的漏洞。

## 决策

1. **平台骨架与业务严格分离**：骨架 = `flexforge-app/common/runtime/auth/system/meta/data/plugin/issue/ai` + 前端 core/通用组件/系统页面。骨架只提供平台能力，不包含任何业务实体、菜单、页面或业务权限种子。
2. **业务一律插件化**：所有业务能力（含用于展示的库存示例）必须以 Level 1+ 插件交付，通过 PluginRuntime 注册；Level 0 仅限平台内核，禁止承载业务。
3. **预置不等于内置**：`plugins/example-inventory` 只作为预置交付物随仓库分发，不写入前后端编译产物、不自动安装。安装/启用/停用/卸载只能调用标准插件 API，与第三方插件完全同权，不设硬编码开关或专用路径。
4. **迁移分区**：根 `database/migrations/` 只允许平台骨架迁移；业务表迁移必须位于插件包内，由插件安装流程执行。
5. **纯净性可验证**：空库执行平台迁移后，系统不得出现任何业务菜单、实体或页面；由 R-GOV-09 与 RB-E2E 回归测试强制。

## 影响

### 正面影响

- 插件生命周期机制对"自带业务"同样成立，演示"停用即消失、卸载即干净"更有说服力。
- 系统骨架保持纯粹，未来任何业务（销售订单、报表等）都走同一条插件接入路径，不会长回骨架里。
- 数据库迁移、菜单、权限、前端页面的归属清晰，便于清理和审计。

### 负面影响

- 演示流程多一步"导入/安装插件"（可用种子脚本一键完成，但脚本必须调用标准 API）。
- Level 0 的"内置编译插件"能力被收紧为平台内核专用，未来若想把复杂业务内置，需要先复审本 ADR。

## 备选方案

1. **演示业务内置 + 配置开关关闭**：不采用。开关是第二条生命周期路径，与插件管理并存会造成双路径状态不一致，正是要避免的屎山源头。
2. **演示业务自动安装**：不采用。自动安装会掩盖安装流程缺陷，且"干净骨架"验收无从成立；采用一键脚本但不自动执行。

## 复审条件

- 出现必须内置才能实现的核心业务能力时，重新论证 Level 0 边界。
- 插件安装成本成为演示障碍时，复审"预置包一键安装脚本"的形态，但不得引入绕过 PluginRuntime 的安装路径。
