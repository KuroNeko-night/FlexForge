# FlexForge 测试策略

## 1. 测试目标

测试重点不是覆盖所有页面，而是证明三条主链路稳定：动态 CRUD、插件生命周期、Agent Issue。每条链路都应能在干净数据库上重复执行。

回归测试分层（提交冒烟/合并回归/阶段回归/发布候选）与治理自检（R-GOV，验证门禁本身未漂移）见 [回归测试计划](./11-regression-test-plan.md)。

## 2. 测试分层

### 单元测试

覆盖领域规则和纯函数：字段类型校验、规格 Schema、插件 manifest 解析、Issue 状态迁移、权限判断、工作流条件判断。

### 集成测试

使用测试数据库验证 Controller、应用服务、迁移和事务行为。重点验证动态数据访问、安装失败回滚和权限过滤。

数据库隔离硬规则：

- 集成/E2E 测试只允许连接一次性 schema 或临时容器（Testcontainers/CI service），禁止指向开发库、演示库或任何有数据的库。
- 破坏性用例（迁移失败、卸载清理、数据删除）只能跑在隔离 fixture 上；测试结束必须清理 schema。
- 测试配置不读取生产/演示环境变量，不落真实用户数据。

插件运行时额外验证：

- `pluginId`、`pluginVersionId`、`activationId` 的身份和并发约束。
- 缺失依赖、迁移失败、重复安装和升级回滚。
- 迁移 runner：脚本顺序、checksum 一致性、重复跳过、越界脚本拒绝（ADR-0005）。
- 停用/卸载时 disposer 清理菜单、权限、监听器和定时任务。
- 旧 activation 的 API、异步任务和前端请求返回 `stale_activation`。

### 端到端测试

至少保留以下冒烟用例：

1. 登录 -> 创建实体 -> 新增/编辑/查询记录。
2. 上传插件 -> 校验 -> 安装 -> 启停 -> 卸载。
3. 创建 Issue -> 规格确认 -> 生成骨架 -> 审核 -> 安装 -> 完成。

## 3. AI 测试

- 使用固定 fixture 测试 JSON Schema 校验和错误修复，不把在线模型作为唯一测试依赖。
- 记录提示词版本、模型名称和结构化输出，便于复现。
- 为缺字段、非法类型、越权字段、超长输入和模型超时准备负例。

## 4. 安全测试

- SQL 注入、路径穿越、恶意插件路径、越权接口和过期 JWT。
- 检查日志脱敏、上传大小限制和文件类型白名单。
- 验证普通用户无法安装插件、修改元数据或跳过 Issue 审核。
- 验证 Level 1 插件无法携带或执行任意 Java/JavaScript 源码。

## 5. 性能基线

使用演示数据量建立可重复基线，不宣称生产级容量。记录动态列表查询、元数据加载和插件安装的 P50/P95，异常时优先优化索引、缓存和序列化。

## 6. 静态质量门禁

- CI 运行格式、lint、文件上限、复杂度和依赖边界检查，违规阻断合并（`NFR-MAINT-01`）。
- `docs/extension-points.md` 中每个 active 扩展点必须有注册-撤销测试；未登记扩展点不得合并（`NFR-MAINT-02`）。
- 依赖边界测试覆盖：无循环依赖、无跨模块 `infrastructure` 引用、未标注 `@PublicApi`/`@ExperimentalApi` 的类不得被跨模块引用。

## 7. 缺陷等级

| 等级 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 | 无法启动、数据损坏、权限绕过 | 立即阻断发布 |
| P1 | 核心演示链路失败 | 当前里程碑内修复 |
| P2 | 非核心功能错误或明显体验问题 | 排入近期迭代 |
| P3 | 文案、样式或低影响改进 | 有余力再处理 |
